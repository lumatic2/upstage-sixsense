전유성 파트 — 여기부터 내 대본 (암기)

706 Upstage 적용 4자리 ★ 20점0:40전유성

핵심: 들어올 때 2(Parse·pro2 식별) + 나갈 때 2(pro2 구조화·이유 / mini 채점). 생성·검증 다른 모델.

"Upstage 제품이 네 자리에서 각자 다른 일을 합니다. 데이터가 들어올 때 둘 — Document Parse가 메뉴판을 읽고, Solar-pro2가 제보 사진에서 가게 이름을 찾아냅니다. 사용자에게 나갈 때 둘 — Solar-pro2가 자연어를 구조화하고 추천 이유를 쓰면, Solar-mini가 그 이유를 실제 데이터와 대조해 채점합니다. 쓴 모델이 자기 답안을 채점하지 않도록 생성과 검증을 다른 모델로 분리했습니다. 참고로 Upstage가 최근 내세우는 말이 '모델이 아니라 문서 구조화가 병목'인데, 저희 파이프라인이 그 말을 메뉴판 사진에서 실물로 증명한 셈입니다."

807 환각 방지 4겹 ★ 차별성0:50전유성

4겹: ①검수 게이트 ②근거 판정(다른 모델) ③기억 검증(마라탕버거) ④추천 칩 검증. 원칙 하나 = 근거 없으면 채택 안 함.

"이 서비스의 차별성은 한 문장입니다 — 근거 없는 말을 내보내지 않는다. 장치가 네 겹입니다. 사람이 확인한 데이터만 쓰는 검수 게이트. 모델이 쓴 추천 이유를 다른 모델이 대조해 근거가 없으면 그 문장을 채택하지 않고 데이터 팩트로 갈아끼우는 근거 판정. 사용자가 '마라탕버거' 같은 없는 메뉴를 말하면 기억에서 지우는 기억 검증. 그리고 '도보 3분 안으로' 같은 제안을 띄우기 전에 실제 결과가 나오는지 먼저 세어보는 추천 검증. 넷 다 원칙은 같습니다 — 근거가 없으면 그 문장을 채택하지 않습니다."

908 정확도·재현성 ★ 15점0:45전유성

핵심: 76.4% 평균 · 지배변수 = 해상도(100% vs 20%) · 원본 응답 저장 → 재호출 없이 0→62.5→76.4% · $0.08.

"정확하게 재봤습니다. 평균 76.4%인데, 평균보다 중요한 건 무엇이 정확도를 가르느냐입니다. 인쇄체에 해상도가 충분하면 100%, 저해상 흐림이면 20% — 지배 변수는 해상도 하나였습니다. 그래서 저해상 사진은 사람 검수가 잡는 구조로 만들었습니다. 그리고 재현성 — API 응답 원본을 저장해두고, 재호출 없이 후처리 규칙만 고쳐가며 0%에서 62.5%, 76.4%로 올렸습니다. 같은 실험을 언제든 다시 돌릴 수 있고, 비용은 전부 합쳐 8센트였습니다."

1009 시행착오 ★0:25전유성

"실제로 겪은 사고 셋만 보여드립니다. Document Parse가 메뉴판을 막대그래프로 오인해 'item_01 12.5'가 나온 적이 있습니다 — 차트 판정이면 폐기하는 규칙을 넣었습니다. '7.0'이라 적힌 가격은 7천원으로 환산하고, 공기밥 천원이 '예산 안의 메뉴'로 뜨던 문제는 본메뉴·사이드 판정 규칙으로 잡았습니다. 원칙은 하나 — 어느 식당에나 통하는 건 규칙으로, 한 가게 사정은 비고로."

질의응답 5분 — 전유성 리드 (상세 방어는 마스터 가이드 §11)

질문답 (한 줄 요지)
"그냥 ChatGPT랑 뭐가 다르죠?" ★범용은 오늘 학식 모르고 가격은 출처·시점 뒤섞인 값. 우리는 1차 소스만 — 오늘 크롤링 HTML + 사람 승인 데이터, 행마다 출처·촬영일·검수자.
"요즘 ChatGPT 웹검색으로 찾잖아요?" ★한 가게는 찾는다. 근데 6천/7천 공존 — 어느 게 지금 값인지 판별 근거가 검색엔 없다. 50곳 예산 필터 질의는 실시간 검색으로 안 된다.
"정확도 76%면 낮지 않나요?"그래서 사람 검수 필수. 인쇄체·고해상이면 100%. 무엇이 정확도를 흔드는지(해상도) 알아낸 게 결과.
"거지맵이랑 뭐가 달라요?"표면은 닮음. 차이는 데이터 생산 — 그쪽 수동 타이핑, 우리 사진→Parse→프리필. 학식 크롤링·상황 자연어 검색은 우리만.
"파싱 틀리면? 데이터 오염은?"전량 자동 반영 안 함. 파싱은 후보까지, 운영자 승인 거쳐야 노출. 자동 경계를 실측으로 그음.
"왜 학식엔 Parse 안 썼나요?"이미 구조화 HTML. 억지 적용은 감점. 비정형=Parse, 정형=크롤러 — 이 구분이 우리 설계.
"전용 Groundedness 모델인가요?" ★정직성아니다. 전용 모델 제공 종료(/v1/models 실측). 같은 계약을 분리된 solar-mini 판정자로. "제품 3종"이 아니라 "Solar 생성·검증 2역할".
"Solar 느리거나 죽으면?"0.7~1.3초, 타임아웃 시 정규식 폴백. source 필드로 경로 투명. mini→pro2 채택도 실측.
"왜 DB 대신 시트?"팀 4명 협업이라. 계정·어드민 없이 누구나 고침. 700행엔 시트가 최소 비용, 커지면 DB로(읽기 경로 하나라 교체 쉬움).
"왜 Parse만? Extract·Classify는?" ★현직자메뉴판은 Parse 좌표+텍스트로 충분. Extract가 할 필드 정리는 도메인 특화 후처리 규칙으로 직접(7.0→7,000·사이드 63케이스·차트 줄 걸러냄) — 더 정확·비용 0. "필요 없어서 우리가 더 정확히" 프레임.
"킥오프의 Supabase·Next.js는 왜 안?"문제 크기에 맞춰 고름. 5화면·얕은 상태라 프레임워크 비용 회수 안 됨. 시트가 곧 어드민(팀 협업·검수). 커지면 옮기면 됨.
